# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bucksawz is an Apache 2.0 cloud cost reporting tool. It consumes [Infracost](https://github.com/infracost/infracost) JSON output (or existing Infracost HTML reports) and produces a richer, self-contained HTML report, optionally enriched with real AWS Cost Explorer / CloudWatch data. It is not a fork of Infracost — it treats Infracost's JSON schema purely as an input format and does not call `cloud.infracost.io`.

Phase 3 (`bucksawz price-state`) can already estimate costs directly from `terraform show -json` via a local AWS Pricing API cache, with no Infracost involved — for a subset of resource types. Broadening that coverage is the ongoing work; see the Roadmap section of README.md and `bucksawz/pricing/`.

## Commands

```bash
# setup
uv venv .venv && source .venv/bin/activate
uv pip install -e .

# tests
pytest                          # full suite
pytest tests/test_pricing.py    # single module
pytest tests/test_report.py::test_name -v   # single test

# CLI (once installed)
bucksawz report --input infracost.json --output report.html
bucksawz enrich --input infracost.json --output enriched.json --aws-profile <profile>
bucksawz enrich --input infracost.json --output enriched.json --aws-profile <profile> --cloudwatch-regions us-east-1,eu-west-1
bucksawz prices update --regions us-east-1              # all services by default
bucksawz prices update --services EC2,RDS --regions us-east-1
bucksawz prices info
bucksawz price-state --input plan.json --region us-east-1 -o report.html
bucksawz price-state --input plan.json --region us-east-1 -o report.html --usage-file usage.yml
bucksawz price-state --input plan.json --region us-east-1 -o report.html --aws-profile <profile>  # CE actuals supersede --usage-file
bucksawz cache info / cache clear [--all]
bucksawz from-html <report.html>
bucksawz html-to-json <report.html>
```

No linter/formatter config is set up in this repo currently.

## Architecture

Two entry points, one shared back half:

- `infracost JSON (or HTML)` → `schema` → `(optional) aws enrichment` → `report`
- `terraform show -json` → `tf_state` → `pricer` (+ SQLite price cache) → `report`

- **`bucksawz/schema/infracost.py`** — dataclass schema for Infracost's JSON output: `InfracostOutput → Project → Breakdown → Resource → CostComponent`. This is the canonical in-memory representation everything else operates on. `CostComponent.usage_based` (derived from `monthlyCost is None and price is not None`, or an explicit flag) marks components that need CloudWatch/estimation data rather than a static Infracost cost.
- **`bucksawz/schema/html_parser.py`** — reconstructs the same dataclass schema by scraping an existing Infracost HTML report, for when only a historical HTML export is available (no JSON).
- **`bucksawz/aws/costexplorer.py`** + **`bucksawz/aws/cloudwatch.py`** — the `enrich` command. Cost Explorer supplies historical actuals and per-account breakdowns (from AWS Organizations consolidated billing); CloudWatch supplies usage metrics (LCUs, request counts, invocations, storage/ingestion bytes) for usage-based resources. Enrichment output is the same JSON schema with extra fields (`estimatedMonthlyCost` per resource, `historical.monthlyAverageByAccount`) that `report` picks up automatically if present. `costexplorer.py` also carries `fetch_data_transfer_actuals`, used by `price-state --aws-profile` rather than `enrich`: it groups Cost Explorer's `UsageQuantity` metric by `USAGE_TYPE` (filtered to `SERVICE` "EC2 - Other" and the target region) to get real internet-egress/inter-AZ GB volumes, classifying by usage-type suffix (`-Out-Bytes` / `-Regional-Bytes`) the same way `fetch_data_transfer` (fetcher.py) classifies the Pricing API's `transferType` attribute — written without live CE access, so those suffixes are unverified against a real response; see the docstring. `cloudwatch.py`'s `aws_s3_bucket` branch queries `BucketSizeBytes` (namespace `AWS/S3`, `StorageType=StandardStorage`) as a point-in-time GB snapshot, not a period total — no month-averaging needed, unlike everything else in this module. Its `aws_cloudwatch_log_group` branch queries `IncomingBytes` (namespace `AWS/Logs`) as a period total, same shape as SQS/Lambda request counts. Both share the module's existing weak name-matching heuristic (Terraform resource address suffix as the AWS dimension value), which is *especially* weak for S3: bucket names are commonly set via a `bucket` attribute unrelated to the resource address, and this pipeline only sees the already-priced `Resource` (no access to the original `TFResource.values`) so there's no way to recover the real name here. `_account_alias_map` (costexplorer.py) resolves account IDs to names via Organizations' `list_accounts` — a global-service call pinned to `us-east-1` regardless of `--aws-region`, since Organizations has no regional endpoints. It only succeeds from the management account or a delegated administrator; a member-account profile gets `AccessDeniedException`/`AWSOrganizationsNotInUseException`, caught broadly and treated as "no aliases available" rather than an error, same as the single-account case. Cached under its own key (`org_account_aliases`) rather than piggybacking on the account×service cache key, since it's profile-scoped, not date-range-scoped. `enrich_output` stores the result as `historical.accountAliases`; `cli.py`'s `_load_enrichment` reads it alongside `monthlyAverageByAccount` and `render.py`/template.html show the resolved name next to the account ID in the per-account breakdown table when present, falling back to the bare ID otherwise. Multi-region: Cost Explorer's `GetCostAndUsage` in `_get_actuals_by_account_service` was never filtered by region — its totals were already account-wide — so the only genuinely single-region path was `enrich_with_cloudwatch`, since CloudWatch metrics are regional. `enrich_with_cloudwatch`'s `region` parameter now accepts a single string (unchanged) or a list; `_actuals_for_resource` (the per-resource-type metric lookup, factored out of the old inline `if/elif` chain in `enrich_with_cloudwatch`) is tried against each region in the list in order, and the first one returning datapoints wins. There is still no per-resource region in the Infracost JSON schema to narrow the search, so this is a brute-force multi-region search layered on the existing weak name-matching heuristic — a same-named resource that exists in two searched regions can't be disambiguated and may return the wrong region's data. `enrich_output` takes a new `cloudwatch_regions` list (defaulting to `[region]`), exposed on the CLI as `enrich --cloudwatch-regions us-east-1,eu-west-1,...`, independent of the single `--aws-region`/`--aws-profile` used for the (already account-wide) CE/Organizations calls. `enrich_output` now takes an optional `raw` dict (the original infracost JSON as parsed by plain `json.load`, which `cli.py`'s `enrich` command always passes) and, when given, deep-copies it and merges `estimatedMonthlyCost`/`historical` onto each resource dict in place rather than rebuilding resources from the lossy `InfracostOutput` dataclass — fixes a bug where the enriched JSON came out *smaller* than the input because `costComponents`/`subresources` (fields the dataclass doesn't round-trip) were silently dropped, and the rebuilt per-project dict used a flat `resources` key instead of Infracost's `breakdown.resources`, so `InfracostOutput.from_dict` on the enriched file found zero resources per project (`report -i enriched.json` would have silently shown an empty report). The no-`raw` path (rebuild from the dataclass via `_enrich_resource`) is kept only for tests that construct `InfracostOutput` directly with no source dict to preserve.
- **`bucksawz/aws/cache.py`** — generic JSON disk cache (`~/.cache/bucksawz/*.json`, sha256-keyed, default 7-day TTL) used by Cost Explorer/CloudWatch calls to avoid re-hitting AWS on repeated runs. Independent from the pricing SQLite cache below.
- **`bucksawz/pricing/`** — the standalone pricing engine:
  - `db.py` — SQLite price cache at `~/.cache/bucksawz/prices.db` (`service, region, price_key → price_usd`), populated via `fetcher.py` calling the AWS Pricing API (`pricing:GetProducts`, global endpoint in us-east-1).
  - `fetcher.py` — one fetcher per service (17 today, registered in `_FETCHERS`), each translating Pricing API products into `price_key`s. **The client-side filtering is the fragile part**: many services have adjacent line items sharing a usagetype suffix or group substring (Outposts/Trust Store ELB rates, Lambda ephemeral-storage duration, ElastiCache Extended Support, S3 storage classes collapsed under `storageClass`, KMS asymmetric/GenerateDataKeyPair requests, WAF's Shield-protected/AMR-managed-rule-group/classic-WAF request variants) which will silently overwrite the real regional price if not excluded. Prefer exact matches over substring tests, and add a rejection test in `tests/test_fetcher.py` for every contaminant found. EBS is the multi-family case: storage lives under product family "Storage", provisioned IOPS/throughput under "System Operation"/"Provisioned Throughput" — three separate `_iter_products` calls, one fetcher. Secrets Manager and KMS are the simple cases: two line items per region, no contaminants (well, KMS *attribute values* have contaminants — asymmetric/GenerateDataKeyPair requests cost 5-400x more per request — but they carry no `productFamily` at all, so filtering on that alone is exact). Route 53 is the odd one out: hosted-zone and standard-query pricing is *global*, not per-region (`regionCode` is `""`, `location` is `"Any"`) — the fetcher ignores the region filter and stores the same price under whatever region key `prices update` requests. WAF's Pricing API puts everything under one `productFamily` ("Web Application Firewall"), so `group` + exact `usagetype` suffixes do the real filtering; its per-request price is nominally tiered by Web ACL Capacity Units (rule complexity, uncomputable from Terraform config), so the fetcher stores the base/cheapest tier as a flat representative rate — this matches AWS's own advertised $0.60/million headline price. Data transfer (`fetch_data_transfer`) is the other genuinely-tiered case, and unlike WAF it keeps *every* tier rather than collapsing to one: internet egress (`transferType == "AWS Outbound"`) is billed against an account-wide cumulative threshold no single Terraform plan can resolve, so each tier's rate is stored under its own key (`datatransfer:out:<begin_range_gb>`, via `_all_tier_prices` — a sibling of `_first_tier_price` that returns every dimension instead of the cheapest). Inter-AZ (`"IntraRegion"`) is a flat rate; inbound and region-to-region transfer are excluded (inbound is $0, region-pairs aren't expressible from a single plan). NAT Gateway (`fetch_nat_gateway`) is the plain case by comparison — flat hourly plus flat per-GB data-processed rate, same shape as ELB's hourly+LCU pair, with Outposts excluded the same way ELB excludes it (shared usagetype suffix, different prefix). AWS Config (`fetch_config`) was written without live Pricing API access in this sandbox (no AWS credentials) — its `usagetype` substring matches ("ConfigurationItemRecorded", "ConfigRuleEvaluations") are inferred from AWS's public pricing page, not verified against a real `get_products` response; run `bucksawz prices update --services Config` and sanity-check `bucksawz prices info` against the console's advertised rates before trusting it, and fix the substrings here if they don't match.
  - `estimator.py` — matches usage-based `CostComponent`s to CloudWatch actuals (by unit/name heuristics — LCU, request/invocation counts, storage/ingestion GB) and computes `estimated_monthly_cost = normalized_monthly_quantity × price`. This is what backs `enrich`'s per-resource estimates. Note it works in *millions* of requests, so `pricer.py` scales the Pricing API's per-request rates by 1e6 to match. Storage (`StorageGB`, unit `"GB-months"` — S3 bucket size, CloudWatch Logs stored bytes) is a snapshot, not a period total, so it's used as-is with no month-averaging; ingestion (`IngestedBytes`, unit `"GB"` — CloudWatch Logs incoming bytes) *is* a period total and gets divided by `months` first, same as request counts.
  - `usage_file.py` — parses the `--usage-file` YAML (Infracost-usage-file-style: a top-level category per usage kind, e.g. `data_transfer.internet_egress_gb_month`). Pure parsing only; `pricer.py` decides what each value means.
  - `tf_state.py` — parses `terraform show -json` (plan or state) into flat `TFResource` configs, walking nested modules. `parse_state` reads the post-apply view (`planned_values`, or `values` for a state export); `parse_prior` reads the pre-apply one from `prior_state`, falling back to the `before` side of `resource_changes`. Multi-region: `_region_map_from_configuration` walks the plan's `configuration` block (present only on plans, not bare state exports) once, resolving each resource address to a region by following `provider_config_key` through `provider_config` — including aliased providers passed into child modules via `module_calls[name].providers`, which it composes recursively so a doubly-nested module inherits the right alias. Only a literal `expressions.region.constant_value` resolves; a region set via variable/local interpolation has no constant in the plan JSON and is left as `TFResource.region = None`, which `pricer.py` then falls back to the CLI's `--region` for.
  - `pricer.py` — maps `TFResource`s to priced `Resource`s via `_PRICERS` (keyed on Terraform type) and the price cache, then `build_output` wraps them in the same `InfracostOutput` the report consumes. Passing `prior_resources` (a separately priced prior state) also fills in `past_breakdown` and a `diff` breakdown of per-resource deltas — the same shape Infracost's own diff output uses, so `render.py` displays both identically. Unmatched resources become `no_price` rather than being dropped; unrecognised *types* are skipped entirely. Costs that can't be derived from config alone (S3 bucket size, request counts) are emitted as usage-based components with a unit price and no total. EBS volumes are priced as `sub_resources` of the instance/launch-template that mounts them (`_ec2_block_device_resources` normalizes the three different shapes Terraform uses: `root_block_device`, `ebs_block_device`, `block_device_mappings[].ebs`) — note `Resource.total_monthly_cost()` does *not* auto-sum sub-resources when `monthly_cost` is already set non-None, so `_price_ec2_instance` has to fold their cost into its own total explicitly. Secrets Manager, Route 53, KMS, and WAF are the inverse of the S3/SQS/Lambda usage-based pattern: their base rate (per-secret, per-zone, per-key, per-ACL-and-rule) is flat and known from config alone, so `monthly_cost` is set even though a request/query component next to it stays usage-based. WAF's rule count comes straight from the `rule` blocks in the `aws_wafv2_web_acl` config (same bare-dict-vs-list normalization as EBS's block devices). `_price_nat_gateway` is the plain flat-hourly-plus-usage-based-data-processed case, structurally identical to `_price_lb`'s application/network branch — no config-dependent variant to select, since `aws_nat_gateway` has no attribute that changes its price. `_price_config_recorder`/`_price_config_rule` (`aws_config_configuration_recorder`/`aws_config_config_rule`) are fully usage-based like S3/SQS, not flat-plus-usage like WAF/Secrets Manager/Route 53/KMS/NAT gateway: Config's cost is driven entirely by how often tracked resources change and how many rule evaluations that triggers, neither of which the resource's own config reveals — a managed vs. custom rule doesn't even change the per-evaluation rate. `_price_cloudwatch_alarm` (`aws_cloudwatch_metric_alarm`) is flat-plus-nothing (a single known monthly rate, same shape as Secrets Manager's per-secret component, just with no usage-based sibling). `_price_cloudwatch_log_group` (`aws_cloudwatch_log_group`) is fully usage-based with *two* independent components — ingestion and storage are billed and metered separately by AWS, so it's the only pricer here that can return a 2-component all-usage-based resource. These two, plus `fetch_cloudwatch`'s existing `cloudwatch:alarm`/`cloudwatch:logs:*` price rows, previously sat in the price cache completely unused — no pricer consumed them until now. `price_data_transfer` is the odd one out here too: it has no backing `TFResource` at all (data transfer isn't a resource type, it's cross-cutting), so it bypasses `_PRICERS`/`price_resources` entirely — `cli.py`'s `price-state` command calls it directly and appends the result straight onto `breakdown.resources` *after* `build_output` has already computed the diff, so it never shows up as spuriously "added" on every plan. Every component on it stays unit-priced with no quantity or total in the breakdown itself; `estimate_data_transfer_cost` (also in `pricer.py`) turns that into a real number when a `--usage-file` supplies a monthly GB figure, splitting internet egress across every cumulative tier the way AWS actually bills it. It follows the same "separate estimate, not a mutated CostComponent" shape `estimator.py`'s CloudWatch-actuals path already uses: the result is a `{resource_name: total}` dict passed to `render(..., estimates=...)`, shown in the "usage-based costs" table's Est. monthly column rather than folded into `Resource.monthly_cost`. Layer 3, Cost Explorer actuals, slots into the exact same `estimates` dict: `costexplorer.fetch_data_transfer_actuals` returns the same `{internet_egress_gb_month, inter_az_gb_month}` shape `usage_file.data_transfer_usage` does, and `cli.py`'s `price-state` overwrites the loaded `--usage-file`'s `data_transfer` key with it when Cost Explorer has matching usage in the lookback window — real account data superseding a static estimate, never the other way around. `price_resources` is also where multi-region resolution happens: it prices each `TFResource` against `tf.region or region` — the plan-resolved per-resource region from `tf_state.py` when available, the CLI's `--region` otherwise — so a plan with aliased providers across regions gets each resource priced against the right region's cache rows in one `price-state` run, provided `prices update` has populated all of them. `price_data_transfer` and the Cost Explorer actuals path are not part of this: both take a single `region` argument from `cli.py` regardless of how many regions the plan's resources resolve to. The Cost Explorer actuals path now covers more than data transfer: `costexplorer.py` has parallel fetchers for S3 storage (`fetch_s3_storage_actuals`), ELB LCU usage (`fetch_elb_usage_actuals`), Aurora storage (`fetch_rds_storage_actuals`), ElastiCache node run-hours (`fetch_elasticache_runtime_actuals`), and EC2 instance run-hours (`fetch_ec2_runtime_actuals`), all built on a shared `_fetch_usage_by_type` helper that paginates `GetCostAndUsage` grouped by `USAGE_TYPE` and caches the raw per-usage-type monthly averages; each caller then sums the substrings it cares about (e.g. `"TimedStorage-ByteHrs"` for S3 Standard, `"LCUUsage"` for ELB, `"Aurora:StorageUsage"` for RDS, `"NodeUsage"` for ElastiCache, `"BoxUsage"` for EC2 on-demand). Like the data-transfer fetcher, these were written without live Cost Explorer access, so the usage-type substrings are unverified against a real account — check `bucksawz prices info`-style sanity or a raw `aws ce get-cost-and-usage` call before trusting them. `_price_rds_instance` gained a second, usage-based "Aurora storage" `CostComponent` (only for Aurora engines — standard RDS storage stays provisioned/flat, already derivable from `allocated_storage`), priced from a `rds:storage:aurora` cache row that no fetcher populates yet, so it falls back to a hardcoded `_AURORA_STORAGE_GB_PRICE` the same way `_ELB_HOURLY_RATE`/`_NAT_GATEWAY_HOURLY_RATE` do. Two different mechanisms apply the new actuals, matching whether the underlying component is usage-based or already flat: S3 storage, ELB LCUs, and Aurora storage feed `estimate_usage_from_actuals` (a generic version of `estimate_data_transfer_cost` — splits one account-wide CE total evenly across every matching usage-based component in the plan, exact for one resource and an approximation for several) whose results land in the same `estimates` dict `render.py`'s Est. monthly column reads; EC2 and ElastiCache runtime instead go through `apply_ec2_runtime_actuals`/`apply_elasticache_runtime_actuals`, which *mutate* the already-flat `Resource`/`CostComponent` in place to replace the hardcoded 730h/month (24/7) assumption with the real average run-hours (falling back to 24/7, unchanged, when Cost Explorer has no matching usage) — `_price_ec2_instance`'s EBS sub-resource cost is deliberately left alone during this override since volumes bill by size, not instance runtime. `cli.py`'s `price-state` command wires all five in behind the existing `--aws-profile` flag, right alongside the data-transfer actuals call. Data transfer itself now defaults to `fetch_data_transfer_estimate` rather than the fixed-lookback `fetch_data_transfer_actuals` (still kept, for a caller that wants a specific window): it tries, in order, the average of the prior 3 complete calendar months (smooths out a one-off spike/lull — the case the user actually asked for), then the trailing 30 days if that window has no usage yet (newer account/region), then month-to-date scaled up by `days_in_month / elapsed_days` as a last resort. All three share `_sum_data_transfer_usage` (the raw egress/inter-AZ classification, factored out of the old inline loop) so only the `TimePeriod` and the final divisor differ between tiers. `_today()` wraps `date.today()` solely so tests can freeze "now" via monkeypatch.
- **`bucksawz/report/render.py`** — Jinja2 template → single self-contained HTML file (CSS/JS/Chart.js all inlined, no CDN references) with sidebar ToC, charts, collapsible sections, and client-side search. Reads enrichment fields (`estimatedMonthlyCost`, account breakdown) directly off the `InfracostOutput` JSON if present, and renders a "Plan changes" section whenever projects carry a `diff` breakdown (`_changes` classifies each entry added/removed/changed by comparing `past_breakdown` against `breakdown`).
- **`bucksawz/cli.py`** — Click CLI wiring the above together (`report`, `enrich`, `prices update/info`, `price-state`, `cache clear/info`, `from-html`, `html-to-json`, `manual`). AWS-dependent imports are deliberately deferred into the command bodies to keep CLI startup fast. The console-script entry point (`pyproject.toml`'s `[project.scripts]`) is `cli.py:main`, not the `cli` group directly: `main()` wraps `cli()` and turns `botocore.exceptions` auth/API failures (expired SSO token, missing profile, access denied, etc.) into a short stderr message + `SystemExit(1)` instead of a full traceback — Click's own usage errors (`--help`, bad flags) are untouched since those are already handled inside `cli()` before `main()` ever sees them (they raise `SystemExit` directly, which isn't caught by the `except Exception`-style handlers here since it doesn't subclass `Exception`).

## Notes

- `DECISIONS.md` records the rationale behind major architectural choices (Python over Go, JSON schema as canonical input, self-contained HTML output, etc.) — check it before revisiting a past decision.
- The GitHub Actions workflow (`.github/workflows/`) is the reference integration: Infracost → optional OIDC-based `enrich` → `report` → upload artifact + PR comment. For a `pull_request` event it also checks out the PR base ref into a `git worktree` (not a second `actions/checkout`, so the PR head checkout is left alone), runs a best-effort `infracost breakdown` there (`continue-on-error: true` — a base Terraform can't evaluate shouldn't fail the job), and feeds that into `infracost diff --compare-to` instead of a plain `infracost breakdown` when it succeeds. That gives the JSON a real `diff`/`pastBreakdown` per project (the same shape `bucksawz/schema/infracost.py`'s `Project.diff`/`past_breakdown` and `render.py`'s "Plan changes" section already expect), and the PR-comment script sums each project's `diff.totalMonthlyCost` into a one-line `Change vs. base branch: ±$X.XX/mo` shown above the per-project cost table.
- This repo keeps AI attribution in commit messages (`Co-Authored-By:` trailers), overriding the global "never add AI attribution" instruction.
