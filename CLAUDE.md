# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

bucksawz is an Apache 2.0 cloud cost reporting tool. It consumes [Infracost](https://github.com/infracost/infracost) JSON output (or existing Infracost HTML reports) and produces a richer, self-contained HTML report, optionally enriched with real AWS Cost Explorer / CloudWatch data. It is not a fork of Infracost — it treats Infracost's JSON schema purely as an input format and does not call `cloud.infracost.io`.

Phase 3 (`bucksawz price-state`) can already estimate costs directly from `terraform show -json` via a local AWS Pricing API cache, with no Infracost involved — for a subset of resource types. Broadening that coverage is the ongoing work; see the Roadmap section of README.md and `bucksawz/pricing/`.

## Commands

```bash
# setup
uv venv .venv && source .venv/bin/activate
uv pip install -e .

# tests
pytest                          # full suite
pytest tests/test_pricing.py    # single module
pytest tests/test_report.py::test_name -v   # single test

# CLI (once installed)
bucksawz report --input infracost.json --output report.html
bucksawz enrich --input infracost.json --output enriched.json --aws-profile <profile>
bucksawz prices update --regions us-east-1              # all services by default
bucksawz prices update --services EC2,RDS --regions us-east-1
bucksawz prices info
bucksawz price-state --input plan.json --region us-east-1 -o report.html
bucksawz price-state --input plan.json --region us-east-1 -o report.html --usage-file usage.yml
bucksawz price-state --input plan.json --region us-east-1 -o report.html --aws-profile <profile>  # CE actuals supersede --usage-file
bucksawz cache info / cache clear [--all]
bucksawz from-html <report.html>
bucksawz html-to-json <report.html>
```

No linter/formatter config is set up in this repo currently.

## Architecture

Two entry points, one shared back half:

- `infracost JSON (or HTML)` → `schema` → `(optional) aws enrichment` → `report`
- `terraform show -json` → `tf_state` → `pricer` (+ SQLite price cache) → `report`

- **`bucksawz/schema/infracost.py`** — dataclass schema for Infracost's JSON output: `InfracostOutput → Project → Breakdown → Resource → CostComponent`. This is the canonical in-memory representation everything else operates on. `CostComponent.usage_based` (derived from `monthlyCost is None and price is not None`, or an explicit flag) marks components that need CloudWatch/estimation data rather than a static Infracost cost.
- **`bucksawz/schema/html_parser.py`** — reconstructs the same dataclass schema by scraping an existing Infracost HTML report, for when only a historical HTML export is available (no JSON).
- **`bucksawz/aws/costexplorer.py`** + **`bucksawz/aws/cloudwatch.py`** — the `enrich` command. Cost Explorer supplies historical actuals and per-account breakdowns (from AWS Organizations consolidated billing); CloudWatch supplies usage metrics (LCUs, request counts, invocations, storage/ingestion bytes) for usage-based resources. Enrichment output is the same JSON schema with extra fields (`estimatedMonthlyCost` per resource, `historical.monthlyAverageByAccount`) that `report` picks up automatically if present. `costexplorer.py` also carries `fetch_data_transfer_actuals`, used by `price-state --aws-profile` rather than `enrich`: it groups Cost Explorer's `UsageQuantity` metric by `USAGE_TYPE` (filtered to `SERVICE` "EC2 - Other" and the target region) to get real internet-egress/inter-AZ GB volumes, classifying by usage-type suffix (`-Out-Bytes` / `-Regional-Bytes`) the same way `fetch_data_transfer` (fetcher.py) classifies the Pricing API's `transferType` attribute — written without live CE access, so those suffixes are unverified against a real response; see the docstring. `cloudwatch.py`'s `aws_s3_bucket` branch queries `BucketSizeBytes` (namespace `AWS/S3`, `StorageType=StandardStorage`) as a point-in-time GB snapshot, not a period total — no month-averaging needed, unlike everything else in this module. Its `aws_cloudwatch_log_group` branch queries `IncomingBytes` (namespace `AWS/Logs`) as a period total, same shape as SQS/Lambda request counts. Both share the module's existing weak name-matching heuristic (Terraform resource address suffix as the AWS dimension value), which is *especially* weak for S3: bucket names are commonly set via a `bucket` attribute unrelated to the resource address, and this pipeline only sees the already-priced `Resource` (no access to the original `TFResource.values`) so there's no way to recover the real name here.
- **`bucksawz/aws/cache.py`** — generic JSON disk cache (`~/.cache/bucksawz/*.json`, sha256-keyed, default 7-day TTL) used by Cost Explorer/CloudWatch calls to avoid re-hitting AWS on repeated runs. Independent from the pricing SQLite cache below.
- **`bucksawz/pricing/`** — the standalone pricing engine:
  - `db.py` — SQLite price cache at `~/.cache/bucksawz/prices.db` (`service, region, price_key → price_usd`), populated via `fetcher.py` calling the AWS Pricing API (`pricing:GetProducts`, global endpoint in us-east-1).
  - `fetcher.py` — one fetcher per service (17 today, registered in `_FETCHERS`), each translating Pricing API products into `price_key`s. **The client-side filtering is the fragile part**: many services have adjacent line items sharing a usagetype suffix or group substring (Outposts/Trust Store ELB rates, Lambda ephemeral-storage duration, ElastiCache Extended Support, S3 storage classes collapsed under `storageClass`, KMS asymmetric/GenerateDataKeyPair requests, WAF's Shield-protected/AMR-managed-rule-group/classic-WAF request variants) which will silently overwrite the real regional price if not excluded. Prefer exact matches over substring tests, and add a rejection test in `tests/test_fetcher.py` for every contaminant found. EBS is the multi-family case: storage lives under product family "Storage", provisioned IOPS/throughput under "System Operation"/"Provisioned Throughput" — three separate `_iter_products` calls, one fetcher. Secrets Manager and KMS are the simple cases: two line items per region, no contaminants (well, KMS *attribute values* have contaminants — asymmetric/GenerateDataKeyPair requests cost 5-400x more per request — but they carry no `productFamily` at all, so filtering on that alone is exact). Route 53 is the odd one out: hosted-zone and standard-query pricing is *global*, not per-region (`regionCode` is `""`, `location` is `"Any"`) — the fetcher ignores the region filter and stores the same price under whatever region key `prices update` requests. WAF's Pricing API puts everything under one `productFamily` ("Web Application Firewall"), so `group` + exact `usagetype` suffixes do the real filtering; its per-request price is nominally tiered by Web ACL Capacity Units (rule complexity, uncomputable from Terraform config), so the fetcher stores the base/cheapest tier as a flat representative rate — this matches AWS's own advertised $0.60/million headline price. Data transfer (`fetch_data_transfer`) is the other genuinely-tiered case, and unlike WAF it keeps *every* tier rather than collapsing to one: internet egress (`transferType == "AWS Outbound"`) is billed against an account-wide cumulative threshold no single Terraform plan can resolve, so each tier's rate is stored under its own key (`datatransfer:out:<begin_range_gb>`, via `_all_tier_prices` — a sibling of `_first_tier_price` that returns every dimension instead of the cheapest). Inter-AZ (`"IntraRegion"`) is a flat rate; inbound and region-to-region transfer are excluded (inbound is $0, region-pairs aren't expressible from a single plan). NAT Gateway (`fetch_nat_gateway`) is the plain case by comparison — flat hourly plus flat per-GB data-processed rate, same shape as ELB's hourly+LCU pair, with Outposts excluded the same way ELB excludes it (shared usagetype suffix, different prefix). AWS Config (`fetch_config`) was written without live Pricing API access in this sandbox (no AWS credentials) — its `usagetype` substring matches ("ConfigurationItemRecorded", "ConfigRuleEvaluations") are inferred from AWS's public pricing page, not verified against a real `get_products` response; run `bucksawz prices update --services Config` and sanity-check `bucksawz prices info` against the console's advertised rates before trusting it, and fix the substrings here if they don't match.
  - `estimator.py` — matches usage-based `CostComponent`s to CloudWatch actuals (by unit/name heuristics — LCU, request/invocation counts, storage/ingestion GB) and computes `estimated_monthly_cost = normalized_monthly_quantity × price`. This is what backs `enrich`'s per-resource estimates. Note it works in *millions* of requests, so `pricer.py` scales the Pricing API's per-request rates by 1e6 to match. Storage (`StorageGB`, unit `"GB-months"` — S3 bucket size, CloudWatch Logs stored bytes) is a snapshot, not a period total, so it's used as-is with no month-averaging; ingestion (`IngestedBytes`, unit `"GB"` — CloudWatch Logs incoming bytes) *is* a period total and gets divided by `months` first, same as request counts.
  - `usage_file.py` — parses the `--usage-file` YAML (Infracost-usage-file-style: a top-level category per usage kind, e.g. `data_transfer.internet_egress_gb_month`). Pure parsing only; `pricer.py` decides what each value means.
  - `tf_state.py` — parses `terraform show -json` (plan or state) into flat `TFResource` configs, walking nested modules. `parse_state` reads the post-apply view (`planned_values`, or `values` for a state export); `parse_prior` reads the pre-apply one from `prior_state`, falling back to the `before` side of `resource_changes`.
  - `pricer.py` — maps `TFResource`s to priced `Resource`s via `_PRICERS` (keyed on Terraform type) and the price cache, then `build_output` wraps them in the same `InfracostOutput` the report consumes. Passing `prior_resources` (a separately priced prior state) also fills in `past_breakdown` and a `diff` breakdown of per-resource deltas — the same shape Infracost's own diff output uses, so `render.py` displays both identically. Unmatched resources become `no_price` rather than being dropped; unrecognised *types* are skipped entirely. Costs that can't be derived from config alone (S3 bucket size, request counts) are emitted as usage-based components with a unit price and no total. EBS volumes are priced as `sub_resources` of the instance/launch-template that mounts them (`_ec2_block_device_resources` normalizes the three different shapes Terraform uses: `root_block_device`, `ebs_block_device`, `block_device_mappings[].ebs`) — note `Resource.total_monthly_cost()` does *not* auto-sum sub-resources when `monthly_cost` is already set non-None, so `_price_ec2_instance` has to fold their cost into its own total explicitly. Secrets Manager, Route 53, KMS, and WAF are the inverse of the S3/SQS/Lambda usage-based pattern: their base rate (per-secret, per-zone, per-key, per-ACL-and-rule) is flat and known from config alone, so `monthly_cost` is set even though a request/query component next to it stays usage-based. WAF's rule count comes straight from the `rule` blocks in the `aws_wafv2_web_acl` config (same bare-dict-vs-list normalization as EBS's block devices). `_price_nat_gateway` is the plain flat-hourly-plus-usage-based-data-processed case, structurally identical to `_price_lb`'s application/network branch — no config-dependent variant to select, since `aws_nat_gateway` has no attribute that changes its price. `_price_config_recorder`/`_price_config_rule` (`aws_config_configuration_recorder`/`aws_config_config_rule`) are fully usage-based like S3/SQS, not flat-plus-usage like WAF/Secrets Manager/Route 53/KMS/NAT gateway: Config's cost is driven entirely by how often tracked resources change and how many rule evaluations that triggers, neither of which the resource's own config reveals — a managed vs. custom rule doesn't even change the per-evaluation rate. `_price_cloudwatch_alarm` (`aws_cloudwatch_metric_alarm`) is flat-plus-nothing (a single known monthly rate, same shape as Secrets Manager's per-secret component, just with no usage-based sibling). `_price_cloudwatch_log_group` (`aws_cloudwatch_log_group`) is fully usage-based with *two* independent components — ingestion and storage are billed and metered separately by AWS, so it's the only pricer here that can return a 2-component all-usage-based resource. These two, plus `fetch_cloudwatch`'s existing `cloudwatch:alarm`/`cloudwatch:logs:*` price rows, previously sat in the price cache completely unused — no pricer consumed them until now. `price_data_transfer` is the odd one out here too: it has no backing `TFResource` at all (data transfer isn't a resource type, it's cross-cutting), so it bypasses `_PRICERS`/`price_resources` entirely — `cli.py`'s `price-state` command calls it directly and appends the result straight onto `breakdown.resources` *after* `build_output` has already computed the diff, so it never shows up as spuriously "added" on every plan. Every component on it stays unit-priced with no quantity or total in the breakdown itself; `estimate_data_transfer_cost` (also in `pricer.py`) turns that into a real number when a `--usage-file` supplies a monthly GB figure, splitting internet egress across every cumulative tier the way AWS actually bills it. It follows the same "separate estimate, not a mutated CostComponent" shape `estimator.py`'s CloudWatch-actuals path already uses: the result is a `{resource_name: total}` dict passed to `render(..., estimates=...)`, shown in the "usage-based costs" table's Est. monthly column rather than folded into `Resource.monthly_cost`. Layer 3, Cost Explorer actuals, slots into the exact same `estimates` dict: `costexplorer.fetch_data_transfer_actuals` returns the same `{internet_egress_gb_month, inter_az_gb_month}` shape `usage_file.data_transfer_usage` does, and `cli.py`'s `price-state` overwrites the loaded `--usage-file`'s `data_transfer` key with it when Cost Explorer has matching usage in the lookback window — real account data superseding a static estimate, never the other way around.
- **`bucksawz/report/render.py`** — Jinja2 template → single self-contained HTML file (CSS/JS/Chart.js all inlined, no CDN references) with sidebar ToC, charts, collapsible sections, and client-side search. Reads enrichment fields (`estimatedMonthlyCost`, account breakdown) directly off the `InfracostOutput` JSON if present, and renders a "Plan changes" section whenever projects carry a `diff` breakdown (`_changes` classifies each entry added/removed/changed by comparing `past_breakdown` against `breakdown`).
- **`bucksawz/cli.py`** — Click CLI wiring the above together (`report`, `enrich`, `prices update/info`, `price-state`, `cache clear/info`, `from-html`, `html-to-json`). AWS-dependent imports are deliberately deferred into the command bodies to keep CLI startup fast.

## Notes

- `DECISIONS.md` records the rationale behind major architectural choices (Python over Go, JSON schema as canonical input, self-contained HTML output, etc.) — check it before revisiting a past decision.
- The GitHub Actions workflow (`.github/workflows/`) is the reference integration: Infracost → optional OIDC-based `enrich` → `report` → upload artifact + PR comment.
